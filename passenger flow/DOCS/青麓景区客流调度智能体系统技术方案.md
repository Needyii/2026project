# 青麓景区客流调度智能体系统技术方案

## 一、项目背景与建设目标

### 1.1 业务背景

青麓景区是城市热门休闲文旅场所，节假日及周末游客流量大、客流波动明显。景区长期存在两类并存的结构性问题：入口区域游客集中扎堆、排队拥堵严重（节假日入口等待实测约 55 分钟，管理层目标 30 分钟），而园区内部多处游览区域客流稀疏、资源空置。目前景区仍依赖人工经验开展客流疏导，一线引导人员无法实时掌握全园各区域动态客流分布，只能凭局部视野和个人经验工作；票务、区域人流、安全巡查、商户运营数据相互独立、各岗位信息不同步，管理层难以提前预判客流高峰、制定科学调度预案。

### 1.2 业务需求发现结论

项目前期已完成 23/36（64%）覆盖度的多岗位访谈与业务需求发现，形成六条候选需求假设（详见《业务需求发现报告》）：

| 编号 | 需求假设 | 优先级 |
|------|---------|--------|
| REQ-1 | 区域分布可见性缺口是入口拥堵与园内空区并存的首要可验证环节 | P0 |
| REQ-2 | 交接"仅发送消息不算完成"的确认机制缺失导致补录与重新核对 | P0 |
| REQ-3 | 安全事件与限流疏散必须保留人工指挥与签核，AI 仅作解释建议 | P0 |
| REQ-4 | 数据新鲜度与接口降级规则需先于调度建议落地 | P1 |
| REQ-5 | 试点指标口径需固定分母与排除规则，避免拆单抬高成功率 | P1 |
| REQ-6 | 反馈闭环需绑定业务编号与资料版本，否则争议无法核对 | P2 |

本技术方案以 REQ-1（可见性）为主干，REQ-3（安全人工兜底）为不可逾越的硬边界，兼顾 REQ-4/5/6 的口径与闭环要求。

### 1.3 建设目标

1. **可见性目标**：为六个岗位提供实时、角色化的全园客流分布视图，补齐"引导员看不到实时区域分布"的信息盲区；
2. **调度目标**：自动识别入口拥堵、园内空区等不均衡状态，输出可落地的人工引导类分流建议，支撑入口等待从 55 分钟向 30 分钟压降；
3. **安全目标**：全程保留人工指挥与签核边界，系统只解释、不执行限流疏散类不可逆动作，预警提前量对齐 10 分钟目标；
4. **合规目标**：严格落实游客隐私保护、聚合统计、权限隔离、留痕审计四类数据红线。

## 二、系统定位与用户角色

### 2.1 系统定位

本系统为面向青麓景区**内部运营人员**的客流均衡调度业务智能体，不面向游客。系统依托票务、点位人流等多源聚合数据实时感知全园客流分布，自动识别不均衡状态，输出可落地的分流调度建议，支撑各岗位协同疏导、风险预警与现场处置。

### 2.2 用户角色与权限矩阵

系统采用岗位角色权限分离机制，六岗位各持独立访问令牌，后端按"行级区域过滤 + 列级字段裁剪"双重策略裁剪数据视图：

| 角色 | 姓名 | 可见数据范围 | 核心功能 |
|------|------|-------------|---------|
| 运营主任 | 顾明岚 | 全园全部数据、所有调度记录 | 总览、预警、建议、**审批确认**、票务、留痕审计 |
| 入口引导员 | 林亦舟 | 仅入口区域实时客流与状态 | 拥堵预警、分流指令接收 |
| 游客服务调度员 | 唐映秋 | 全园区域密度、空区信息 | 建议接收、全域调配（无确认权） |
| 票务数据工程师 | 秦芮 | 票务出票、入园流量聚合 | 数据校准、历史趋势（不参与现场调度） |
| 安全负责人 | 傅景 | 高人流风险区、拥堵与异常告警 | 安全巡查、风险管控（无建议生成权） |
| 商户服务代表 | 叶书 | 仅商户片区比例与趋势 | 客流预判、经营调配（无绝对人数） |

## 三、总体架构设计

系统采用四层架构，自下而上依次为数据层、服务层、智能体层与展示层：

### 3.1 数据层

SQLite 单文件数据库（WAL 模式），包含四类表：

- **region_flow**：区域客流聚合现状（区域 ID、名称、类型、容量、当前聚合人数、更新时间）；
- **flow_history**：区域客流历史序列，支撑趋势图与回溯，按保留时长定期清理；
- **ticket_stats**：票务出票/入园聚合统计，独立数据域，供票务工程师与运营主任查看；
- **dispatch_log**：调度留痕表，由数据库触发器**禁止 UPDATE/DELETE**，从存储层保证记录不可篡改；
- **access_audit**：访问审计表，记录每次请求的角色、路径、放行/拦截结果。

### 3.2 服务层

FastAPI（Python 3.13）承载全部 REST 接口与 WebSocket 推送。鉴权采用 Bearer Token 模式，六岗位令牌与角色映射、数据边界统一维护于权限模型模块，接口层通过依赖注入完成校验，越界请求统一返回 403 结构体并写入审计。

### 3.3 智能体层

调度建议采用"规则引擎兜底、LLM 增强"的双轨设计：

- **规则引擎（已实现）**：基于占容量比阈值判定拥堵（≥80%）与空区（≤30%），将拥堵入口与空闲园区配对生成"引导分流"建议；每条建议附带唯一编号、数据依据、安全声明，并硬编码动作黑名单（限流、疏散、关闭闸机等），规则层与确认接口双重拦截；
- **LLM 增强（规划）**：通过 OpenAI 兼容接口接入大模型（配置于 config.yaml，密钥不进代码），用于将规则建议转写为面向不同岗位的自然语言解释文本，不参与安全类决策。

### 3.4 展示层

Vue 3 + Vite + ECharts 构建六角色可视化工作台，全园热力分布图、区域趋势曲线、预警列表与调度建议卡片，通过 WebSocket 按"模拟器同频"节奏实时刷新。

## 四、技术选型与依据

| 层 | 选型 | 版本 | 选型依据 |
|----|------|------|---------|
| 后端框架 | FastAPI + Uvicorn | ≥0.115 | 异步原生、依赖注入天然适配权限拦截、内置 WebSocket |
| 数据库 | SQLite（WAL） | 3.x | 单文件零部署，满足"不引入多余中间件"约束，触发器可实现存储级防篡改 |
| 前端 | Vue 3 + Vite + ECharts | Vue≥3.4 | 团队 Node 22 环境就绪；ECharts 热力图/趋势图组件成熟 |
| 智能体 | 规则引擎 + OpenAI 兼容 LLM | — | 确定性调度逻辑不依赖模型，保证可审计；LLM 仅做解释增强 |
| 配置管理 | config.yaml | — | 密钥、模型地址、阈值统一配置，禁止写死在代码 |
| 实时推送 | WebSocket | — | 客流分布秒级刷新，无需引入 Redis/MQ 等外部中间件 |

## 五、数据红线与安全设计

六条数据红线全部在代码层硬落地，不依赖约定：

| 红线 | 落地机制 |
|------|---------|
| 1. 禁止采集存储游客隐私 | 全库无任何个人字段，数据模型仅含区域聚合值 |
| 2. 只统计区域人数聚合值 | 模拟器/接口输出均为区域级计数，无定位与轨迹 |
| 3. 角色权限严格隔离 | Token→角色→边界三层校验，越界 403 并写审计；商户视图列级裁剪隐藏绝对人数 |
| 4. 原始票务/录像不透出 | 仅提供聚合统计接口，无原始明细通道 |
| 5. 调度记录留痕不可篡改 | dispatch_log 数据库触发器 RAISE ABORT 禁改禁删，已通过直连数据库攻击用例验证 |
| 6. 禁止导出原始明细 | 不提供任何导出类接口与函数 |

安全边界设计对齐需求报告 REQ-3：系统仅输出人员引导类建议（requires_human=true），不触碰闸机、广播、限流、疏散通道；调度确认权仅限运营主任，确认动作再次过安全黑名单审查，命中即返回 SAFETY_BLOCKED。

## 六、核心功能设计

### 6.1 实时客流感知模块

模拟器/真实数据源按固定周期写入各区域聚合人数，提供现状查询、历史趋势、票务聚合三类数据服务。当前以模拟器驱动（对齐"入口高水位、园内空置"真实基线），接口协议与真实数据源一致，后续替换数据源仅改模拟器模块。

### 6.2 智能调度建议模块

规则引擎每轮刷新生成建议列表：拥堵入口×空区配对分流、园内异常升温安全关注提示。建议结构含编号、区域、动作、去向、数据依据、人工确认要求与安全声明。

### 6.3 调度确认与留痕模块

建议经运营主任人工确认后写入防篡改留痕表，形成"建议→确认→留痕"闭环，对齐交接确认机制（REQ-2）。留痕单号可供审计接口回查。

### 6.4 角色化视图模块

同一客流数据按六角色裁剪为不同视图，经 REST 与 WebSocket 双通道下发，行级（区域类型）与列级（敏感字段）双重过滤。

## 七、接口设计

所有接口统一返回结构 `{"ok": bool, "data": ..., "error": {"code": str, "msg": str}}`：

| 接口 | 方法 | 可用角色 | 说明 |
|------|------|---------|------|
| /api/health | GET | 公开 | 健康检查 |
| /api/flow/overview | GET | 六岗位 | 角色化全园客流总览（含预警项） |
| /api/flow/history/{region_id} | GET | 运营/调度/票务/商户（限商户片区） | 区域历史趋势 |
| /api/ticket/stats | GET | 运营主任、票务工程师 | 票务出票/入园聚合 |
| /api/dispatch/suggestions | GET | 运营主任、调度员 | 当前调度建议列表 |
| /api/dispatch/confirm | POST | 运营主任 | 人工确认建议并留痕（含安全黑名单审查） |
| /api/dispatch/log | GET | 运营主任 | 调度留痕审计查询 |
| /ws/flow | WebSocket | 六岗位 | 实时推送角色化客流视图 |

## 九、部署与环境要求

- **硬件**：普通办公主机即可（开发环境为 32GB 内存 / i7 处理器，服务端资源占用极低）；
- **软件**：Python 3.13+、Node 22+（前端构建）；SQLite 随 Python 标准库内置，无独立部署项；
- **配置**：全部可变参数集中于 config.yaml（监听地址、端口、令牌、LLM 地址与密钥、阈值、区域清单）；
- **启动**：`python -m pip install -r requirements.txt` 后运行 `python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000`，自测执行 `python verify_phase1.py`。

## 十、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| SQLite 并发写锁 | 高频调用偶发 database is locked | 已启用 WAL；并发上量前迁移 PostgreSQL |
| 模拟数据与真实口径偏差 | 阈值失真、误报 | 接入真实票务数据后按 REQ-5 重校口径（固定分母、排除规则、统计周期） |
| 演示级令牌体系 | 无过期、无审计强度 | 阶段三切换 JWT/账号体系，接入访问有效期与刷新机制 |
| LLM 建议越界 | 触碰安全红线 | 规则引擎黑名单 + 确认接口二次审查 + 人工签核三重防线，LLM 仅解释不决策 |
| 需求仍为待验证假设 | 试点方向偏差 | 保持"假设→试点→复测"节奏，验收以计数误差<5%与人工转人工时效为准 |

## 十一、预期产出与验收标准

1. 六岗位角色化实时客流工作台（热力图 + 趋势 + 预警 + 建议卡片）；
2. "建议→人工确认→留痕审计"完整调度闭环，留痕不可篡改可审计；
3. 试点验收硬指标：两个入口计数误差低于 5%、安全事件及时转人工、入口等待向 30 分钟目标收敛、拥挤告警提前量趋近 10 分钟；
4. 全套自测与验证脚本，覆盖鉴权、越界拦截、安全红线、防篡改四类关键用例。
